# Video Studio 全量重构设计：故事调查型科普内容工作台

日期：2026-08-17
状态：已获产品方向批准，等待书面规格复核

## 1. 背景与目标

当前系统能完成从主题到成片的自动化流水线，但文案质量不足：内容依赖单次 LLM 生成，没有独立调查环节；固定五段式、固定反转和固定口头禅让稿件高度同质；字幕、封面、JSON 格式和字数约束在写作阶段争夺模型注意力；所谓“去 AI 味”主要依靠禁词，无法建立真实作者感。

本次不保留历史兼容性，重建整个项目。第一优先级是文案，目标产品定义如下：

- 内容类型：故事调查型科普；
- 目标观众：18–35 岁泛知识用户；
- 视频时长：由选题和故事决定，通常为 60 秒至 6 分钟；
- 事实策略：表达效果优先，但支撑故事成立的结论、高风险数字和明显可疑内容必须核验；
- 人工节点：用户选择故事切口，并审阅、批注初稿；
- 文风要求：不使用固定话术和固定结构，以具体调查过程形成自然作者声音；
- 重构方式：新系统通过验收后删除旧实现、旧数据、旧成片和旧 Git 历史，以唯一新根提交替换 `master`。

## 2. 非目标

- 不做逐句论文式引用，不要求普通背景常识全部附带来源；
- 不把系统设计成无人参与的全自动内容工厂；
- 不用多个模型生成三篇完整稿件再拼接；
- 不用一个综合 AI 分数替代人工编辑判断；
- 不在新系统中保留旧 prompt、旧状态字段、兼容 wrapper、迁移适配器或旧实现副本；
- 不在 Content Studio 第一阶段同时重建全部视频渲染能力。

## 3. 总体交付顺序

重构拆成两个独立项目周期：

1. 建设 Content Studio，完成调查、切口、写作、审稿、版本管理和文案导出；
2. 重建视频生成与发布系统，使其只消费已经批准的新文案协议；
3. 两个系统通过端到端验收后，执行旧项目清理、建立新根提交并替换远端历史。

旧系统在验收阶段仅用于盲测基线。清理完成后不保留旧实现或旧产物。

## 4. 产品主流程

```text
主题
  → 选题诊断
  → 调查材料包
  → 三个故事切口
  → 人工选择或修改切口
  → 叙事路线图
  → 自由初稿
  → 人工编辑与批注
  → 定向重写
  → 文案批准
  → 口播适配
  → 分镜、配音、字幕、渲染与发布
```

### 4.1 选题诊断

诊断主题真正值得追查的问题、观众已有认知、核心矛盾、常见误解、建议范围和明确不讲的内容。此阶段不写钩子或全文。

### 4.2 调查材料包

整理核心机制、事实卡片、人物与事件、具体场景、可视化细节、争议和不确定性。材料服务于后续选择，不直接按照材料顺序写稿。

### 4.3 三个故事切口

三个切口必须在调查问题或证据路径上有本质区别，不能只是替换开场句。每个切口包含：

- 调查问题；
- 开场场景；
- 证据路线；
- 最终发现；
- 适用理由；
- 预计时长；
- 事实或叙事风险。

用户可以选择、直接编辑、针对单个切口给反馈后重做，或要求全部换方向。重新生成始终创建新版本，不覆盖旧结果。

### 4.4 叙事路线图

根据选中的切口自由选择叙事方式。可使用异常追查、历史还原、因果追踪、实验推演、人物跟随或争议辨析等模型，但这些只是工具，不是固定模板。

路线图中的每个段落必须声明：叙事任务、使用的事实卡片、推进的新信息、引出的下一个问题，以及不能提前泄露的内容。

### 4.5 自由初稿

作者只处理内容、叙事和声音，不接收封面、高亮坐标、字幕行长、JSON 包装或固定字数要求。路线图完成后估算时长；内容过多时缩小调查问题，内容不足时缩短视频，不通过注水或高速压缩满足预设时长。

### 4.6 人工批注与定向重写

用户可以直接编辑正文，也可以按文字范围或段落添加“没讲懂、太套路、缺证据、节奏慢、删掉、保留原句”等批注。每条批注可选择交给 AI 处理或仅作人工备注。

重写前展示本轮处理范围；重写后展示逐段差异，由用户接受或拒绝。标记为“必须保留”的文字不得改变。系统不提供无目标的“一键润色全文”。

### 4.7 文案批准与口播适配

批准后锁定 `editorial_text`，再派生 `speech_plan`。口播编辑只能调整发音、停顿、重音和字幕语义块，不能增加事实、改变结论或重排叙事。若配音时长不合适，系统提示退回审稿，不在后台偷偷删稿。

## 5. 去 AI 味设计

### 5.1 从结构而非禁词入手

删除现有 prompt 中的预制话术，包括但不限于“你以为……其实……”“这就有意思了”“离谱的是”“说白了”“关键是”“没了”。不要求刻意使用“你”“我”，也不要求每篇都有反常识和反转。

目标声音定义为：一个真的查过这个问题的人，把自己的调查过程讲给一个聪明但不了解该领域的人听。

### 5.2 段落推进约束

每段至少承担一种真实功能：提出疑点、给出线索、排除解释、补充必要背景、建立因果、制造新问题、修正认知或完成发现。没有新增事实、没有推进调查、只表达情绪的段落应删除。

### 5.3 跨稿件结构指纹

系统保留近期 20–50 篇新系统稿件的结构指纹，检测：

- 相同开头句式；
- 高频转折词；
- 相同反转位置；
- 相同结尾结构；
- 重复类比；
- 连续使用“先误导、再纠正”的套路。

重复度过高时退回叙事路线图，不做同义词替换。这里保留的是新系统正常业务数据，不包含被清理的旧项目历史。

## 6. 内容数据模型

### 6.1 `TopicDiagnosis`

- `core_question`
- `audience_prior_knowledge`
- `central_tension`
- `misconceptions`
- `scope`
- `excluded_topics`

### 6.2 `ResearchPacket`

- `mechanisms`
- `fact_cards`
- `people_events`
- `concrete_scenes`
- `visual_details`
- `uncertainties`
- `sources`

事实卡片至少记录 claim、叙事价值、置信度、风险类型和可选来源。

### 6.3 `StoryPitch`

- `investigation_question`
- `opening_scene`
- `evidence_path`
- `payoff`
- `why_it_works`
- `estimated_duration_sec`
- `risks`

### 6.4 `NarrativePlan`

由有稳定 ID 的段落计划组成；每段包含 purpose、fact references、new information、next question 和 withheld information。

### 6.5 `DraftRevision`

- 正文及稳定段落 ID；
- 对应路线图版本；
- 父版本；
- 变更来源；
- 作者选择说明；
- 创建时间。

### 6.6 `EditorialComment`

- 锚定段落和可选文字范围；
- 批注类型与用户原话；
- 是否允许 AI 处理；
- 处理状态及对应 revision。

### 6.7 `ApprovedScript`

包含不可被下游隐式修改的 `editorial_text`、批准 revision、内容结构和事实引用。

### 6.8 `SpeechPlan`

包含口播文本、发音、停顿、重音、字幕语义块和预计朗读时长，并记录其来源 `ApprovedScript` revision。

## 7. 轻量事实核验

- 普通常识允许模型直接使用；
- 支撑故事成立的核心结论必须核验；
- 精确数字、历史日期、世界第一、唯一、倍数关系和绝对化表述自动标记为高风险；
- 找不到可靠依据时，将表达改成模糊但诚实的范围，或删除该材料；
- 来源显示在调查材料和编辑界面，不要求在旁白中逐条朗读；
- 低置信度事实不能成为故事最终发现的唯一支撑。

## 8. 模型调用边界

每个角色使用独立、短小的新上下文：

- 调查员找材料，不写金句；
- 选题编辑设计切口，不写全文；
- 结构编辑安排信息顺序；
- 作者只使用批准材料和路线图写稿；
- 审稿员指出具体问题，不自动重写；
- 重写员只处理用户允许处理的批注；
- 口播编辑不能改变事实和结论。

所有模型经统一 provider 接口调用，模型、参数和凭证属于配置，不进入业务逻辑。每个阶段使用严格 schema 校验。

失败策略：

- schema 错误只做一次格式修复，不重新创作内容；
- 材料不足时停止并建议缩小问题或更换切口；
- 三个切口相似时只重做相似项；
- 初稿偏离路线图时退回作者；
- 重写破坏保留文字时拒绝新版本；
- 达到重试上限后保留已有结果，交由用户决定。

## 9. 技术架构

采用模块化单体，不拆微服务：

```text
Web Studio
    → Content Engine
    → SQLite + persistent job worker
    → Approved Script
    → Speech / Visual / Rendering / Publishing adapters
```

建议模块边界：

```text
studio/
  topics/
  research/
  pitches/
  narratives/
  writing/
  editorial/
  speech/
  visuals/
  rendering/
  publishing/
```

SQLite 替换 JSON job 文件。阶段转换和 revision 写入必须使用事务；worker 使用持久化 claim/lease，进程中断后自动恢复。不同模块只交换版本化结构对象，不读取彼此私有文件。

Content Studio 和视频系统通过 `ApprovedScript` / `SpeechPlan` 协议解耦。任何下游模块都不能修改已批准正文。

## 10. Web 页面与交互

### 10.1 项目首页

首页按草稿、等待选切口、等待审稿、已定稿、制作中和已完成展示项目。新建项目默认只要求主题；受众、事实策略等高级选项折叠显示。

### 10.2 统一工作台

顶部步骤条固定展示：

```text
选题诊断 → 调查材料 → 选择切口 → 初稿 → 审稿 → 定稿 → 视频
```

当前阶段占据主区域。修改上游结果前，明确提示将失效的下游版本。长任务通过 SSE 推送具体进度，不轮询和刷新整个页面。

### 10.3 切口选择页

三个卡片并列展示调查问题、开场场景、证据路线、最终发现、预计时长和风险。支持选择、编辑、单卡重做、全部换方向和展开调查材料。所有重新生成都创建版本。

### 10.4 初稿审阅页

桌面端为路线图、正文、批注与检查三栏；移动端为三个页签。正文直接编辑并自动保存；选择文字即可添加批注。AI 重写必须先显示处理范围，完成后展示逐段 diff。

### 10.5 检查面板

检查项包括：可疑数字、因果跳跃、跨稿件重复、未推进调查的段落、难以口播的句子、预计时长和建议拆题位置。提示必须定位具体段落，可以忽略并保存原因，不输出虚假综合分数。

### 10.6 定稿与视频页

批准文案后依次进入口播字幕预览、分镜预览、配音试听、视频渲染和发布下载。修改正文必须显式退回审稿，并告知将失效的口播、分镜和渲染版本。

### 10.7 错误交互

长任务显示当前具体工作。失败时提供可读原因、当前阶段重试、修改输入后重试、保留上游结果及折叠的技术详情。

## 11. 质量评测与验收

### 11.1 固定评测集

建立 24–30 个新选题，覆盖自然机制、日常疑问、历史调查、商业社会机制、争议题以及材料不足的弱选题。更换模型、prompt 或流程后必须回归。

### 11.2 人工盲评维度

1. 是否愿意继续听；
2. 调查问题是否明确；
3. 每段是否推进发现；
4. 是否真正解释清楚一个机制；
5. 是否存在固定话术或强行反转；
6. 是否像一个有判断的人在讲；
7. 核心事实是否可信；
8. 是否与近期稿件结构重复。

### 11.3 验收线

- 与旧系统盲测时，新稿总体偏好率至少 75%；
- “固定话术明显”的人工评价低于 10%；
- 三个切口的有效差异率至少 90%；
- 支撑故事成立的核心结论全部完成轻量核验；
- 用户标记的保留文字在 AI 重写中 100% 不变；
- 口播适配不改变事实、结论和叙事顺序；
- 任务中断可以恢复，不产生重复 revision 或状态覆盖。

### 11.4 测试层次

- 纯逻辑测试：schema、状态迁移、版本差异、批注锚点、重复检测；
- 模型契约测试：fake provider 验证各阶段字段权限；
- 固定响应集成测试：完全离线运行完整文案流程；
- 少量在线评测：显式手动触发，与默认测试隔离。

默认测试必须离线，不读取真实密钥、不访问真实生产数据、不写系统日志目录。

## 12. 切换与不可恢复清理

执行清理前必须同时满足：

1. 新 Content Studio 达到文案验收线；
2. 新视频流水线成功消费批准文案；
3. 新系统至少完成一个真实端到端项目；
4. 已列出并核对需要保留的密钥、BGM、字体和音色资产；
5. 已生成精确删除清单，并确认目标全部位于本项目范围；
6. 新代码和必要资产已经形成可验证的最终工作树。

清理动作包括：

- 删除旧源码、旧 prompt、旧测试、旧文档和所有兼容层；
- 删除旧 `jobs/`、`runs/`、archive、日志、缓存、trigger、lock 和历史成片；
- 移除旧 systemd path/service 机制；
- 清除旧 Git 提交历史；
- 以新项目最终内容创建唯一根提交；
- force push 新 `master`，替换远端历史。

运行密钥与用户明确要求保留的媒体资产不进入 Git，也不因仓库历史清理而删除。清理前必须依据精确路径逐项解析目标；不得对工作区根目录、用户主目录或未解析变量执行递归删除。

## 13. 设计完成定义

当 Content Studio 与新视频系统均通过验收、旧系统完成不可恢复清理、远端 `master` 只包含新根提交，且新项目可以从文档化配置重新部署并完成端到端任务时，本次全量重构才算完成。
